# 生产级准入验收测试报告（PoV Gate 1 – 4）

除基础功能验收（[V1 – V8 测试指南](verification-guide.md)）外，针对企业核心生产环境重点关注的**宿主机例行维护无感迁移、长期高负载内存与网卡稳定性、线上网络参数热调、大规模弹性扩缩容与优雅停机排空**四大场景，我们基于本仓库构建的自定义镜像完成了全套生产级准入压测（Production PoV Gate）。

### 第 3 项：驱动状态机重置与参数热调测试 — ✅ PASS

#### 1. 测试设计
在配置了最大巨帧 `MTU 8896` 的 VPC 网络内，对运行中的 `n4-standard-4` 实例连续在线执行 **20 轮循环**（每轮包含 5 次队列重建动作，合计 **100 次** `DQO_QPL` 收发队列销毁与重分配），并实时测量每次操作后的恢复延迟：
1. `ethtool -G eth0 rx 2048` $\leftrightarrow$ `ethtool -G eth0 rx 1024`（在线调整接收环形队列深度）；
2. `ip link set dev eth0 mtu 8896`（附 `ping -M do -s 8868` 禁分片巨帧实测）$\leftrightarrow$ `ip link set dev eth0 mtu 1460`（附 `ping -M do -s 1432` 标准帧校验）；
3. `ip link set dev eth0 down && ip link set dev eth0 up`（网卡接口状态机完整重置）。

#### 2. 实测结果

| 热调操作项（各循环 20 次） | 最小恢复耗时 | 平均恢复耗时 | 最大恢复耗时 | 丢包 / 异常 |
| :--- | :---: | :---: | :---: | :---: |
| **`ethtool -G eth0 rx 2048` 在线扩环恢复连通** | `2.58 ms` | **`4.82 ms`** | `6.19 ms` | `0%` / 无异常 ✅ |
| **切换 `MTU 8896` 并通过 `8868B` 禁分片巨帧 Ping** | `1.72 ms` | **`1.96 ms`** | `2.20 ms` | `20/20` 全通 (`0%` 丢包) ✅ |
| **切回 `MTU 1460` 并通过 `1432B` 禁分片标准帧 Ping** | `1.62 ms` | **`1.87 ms`** | `2.21 ms` | `20/20` 全通 (`0%` 丢包) ✅ |
| **`eth0 down -> up` 底层物理 Carrier 重协商恢复** | `29.59 ms` | **`37.52 ms`** | `53.07 ms` | 无异常 ✅ |
| **`eth0 down -> up` Carrier 就绪后三层 ICMP 恢复** | `1.79 ms` | **`2.19 ms`** | `2.71 ms` | `0%` 丢包 ✅ |

* **引用计数与内核内存核查**：100 次队列销毁/重建前后 `/sys/module/gve/refcnt` 均保持 `0`（无模块引用计数泄漏），内核 `Slab` 占用无增长（`39,640 kB -> 39,468 kB`），`tx_timeouts = 0`，`dmesg` 零 `Oops` / `WARNING`。

> **运维操作提示**：
> 1. **存量实例启用巨帧 (`MTU 8896`)**：若将现有 VPC 网络的 MTU 从 `1460` 修改为 `8896`，已处于运行状态的存量实例需执行一次关机再启动（`stop` $\rightarrow$ `start`）以刷新虚拟网卡硬件最大 MTU 描述符；新建实例则直接生效。
> 2. **远程测试 `eth0 down/up` 防失联**：切勿在交互式 SSH 会话中分两行手动输入 `ip link set dev eth0 down`（敲下回车后网络即断，第二行 `up` 无法送达），必须通过后台本地脚本在同一进程内连续执行 `ip link set dev eth0 down && ip link set dev eth0 up`，由于耗时仅约 `40 ms`，处于 TCP 重传容忍窗口内，当前 SSH 会话本身也不会断开。

### 第 4 项：弹性扩缩容（MIG）批量冷启动、ACPI 优雅关机与连接排空测试 — ✅ PASS

#### 1. 20 节点并发冷启动与自动扩盘实测
使用托管实例组（Managed Instance Group）基于 `10 GB` 基础自定义镜像一次性并发拉起 **20 台** `n4-standard-2` 实例（指定 `20 GB` `hyperdisk-balanced` 启动盘），并挂载至区域内部直通式网络负载均衡器（开启 `--connection-draining-timeout=30s`）：
* **并发冷启动成功率**：**`20 / 20 (100%)`**，实例组从 `0` 并发创建至 20 台全部 `RUNNING` 总耗时 **`37 秒`**；
* **实例内部冷启动耗时（`systemd-analyze`）**：**`12.960 秒`**（`1.268s kernel + 2.684s initrd + 9.006s userspace`，精准落在 `10–15 秒` 目标区间内）；
* **根分区在线自动扩容**：20 台节点根文件系统 `100%` 自动在线扩容至 **`19.39 GiB`（`df -h /` 显示 `20G`）**；
* **负载均衡健康检查**：挂载后端后 **`24 秒`** 内全部达成 **`20 / 20 HEALTHY`**，`proto 66` 本地 VIP 路由 `100%` 自动下发。

#### 2. 双轨连接排空（Connection Draining）与 ACPI 优雅停机深度验证
为验证缩容期间“**新连接不再发往排空实例，而排空窗口内的已建立存量长连接继续保持不中断，直至排空结束后优雅执行 ACPI 停机脚本**”，在触发实例组 `resize 20 -> 10` 缩容全过程中同时间轴并发运行三条流量轨道：
* **轨道 A1（存量 `HTTP/1.1 Keep-Alive` 长连接）**：缩容前预先通过负载均衡 VIP 建立并锚定覆盖全部 20 台后端的 20 条持久 TCP 长连接（每 `0.5s` 复用同一 Socket 收发请求并校验单连接递增序号）；
* **轨道 A2（在途长耗时慢请求）**：触发缩容前夕在另外 20 条已建立长连接上并发发起耗时 **`18.0 秒`** 的在途慢请求，横跨控制面摘流切换点；
* **轨道 B（`50 QPS` 新建短连接）**：4 线程持续以 **`50 QPS`** 向 VIP 发起全新 TCP 短连接（`Connection: close`），验证新流量实时摘除表现；
* **ACPI 优雅关机回执**：每台实例配置 `shutdown-script`，收到平台下发的 ACPI 关机信号后由 `google-shutdown-scripts.service` 优雅停止业务进程，并在 `gve` 网卡下线前向观测端发送包含停机耗时与 `tx_timeouts` 统计的 JSON 停机凭证。

**双轨并发实测结果**：
1. **`50 QPS` 新建连接实时摘流（`100%` 成功，`0` 报错）**：全程累计发起 **`8,528` 次**全新短连接请求，**`8,528 / 8,528 (100.0%)` 返回 `200 OK`（`error_count = 0`）**。控制面摘流生效后，全部 10 台缩容节点立即彻底停止接收任何新连接（后续整个排空窗口内落入缩容节点的新连接数为 **`0`**，100% 平滑路由至 10 台保留节点）。
2. **存量长连接与 18 秒在途慢请求完整保持（零中断）**：
   * 在新连接已被完全切断之后，锚定在 10 台缩容节点上的 **10 条存量 Keep-Alive 长连接仍然保持在原实例上继续正常通信 `80.05 秒 – 81.14 秒`**，期间每条单连接在零新连接进入的状态下继续成功处理 **`160 – 162` 次**请求（单 Socket 累计复用达 `247 – 249` 次），直至排空期满业务进程优雅关闭返回 `FIN`，客户端随即自动重连 VIP 无缝切换至保留节点；
